# Schema — قوانین ویکی دانش این پروژه

> این فایل قوانین ساختار و نگه‌داری `docs/wiki/` را تعریف می‌کند. ایجنت (و هر مشارکت‌کننده) موظف است این قوانین را رعایت کند.

## چیست و چرا
ویکی دانش زنده و append-friendly کنار کد؛ به‌جای re-scan کردن کل کدبیس در هر مکالمه، خلاصه‌ی entity ها (مدل‌ها، سرویس‌ها، صفحات، کامپوننت‌های کلیدی) و concept ها (flowها، الگوها، تصمیم‌های معماری) را نگه می‌دارد.

## ساختار پوشه
```
docs/wiki/
  schema.md      # همین فایل — قوانین
  overview.md    # یک‌نگاه کلی پروژه (≤۴۰۰ کلمه)
  index.md       # کاتالوگ همه صفحات، گروه‌بندی‌شده، خلاصه یک‌خطی
  log.md         # تاریخچه append-only (جدیدترین در پایین)
  entities/      # هر entity مهم یک صفحه (مدل دیتا، service، route، صفحه/کامپوننت کلیدی UI)
  concepts/      # patternها، flowها، قراردادها، تصمیم‌های معماری
  sources/       # (اختیاری) خلاصه فایل‌های خام کدی که چندجا ارجاع داده می‌شوند
```

## شروع هر مکالمه/سشن
1. اول `overview.md` و `index.md` را بخوان. هرگز کل کدبیس را re-scan نکن.
2. فقط صفحات مرتبط با تسک فعلی را drill-down کن (`entities/*.md`, `concepts/*.md`).

## وقتی کد تغییر کرد — قانون اکید
هر بار که یک فایل پروژه (خارج از `docs/wiki/` و خارج از `.noqte/`) Write/Edit می‌شود:
1. تشخیص بده این تغییر روی کدام entity/concept اثر می‌گذارد.
2. صفحه‌ی مربوطه را به‌روز کن (فیلد جدید/حذف‌شده، امضای تابع، route جدید، dependency جدید، edge case).
3. اگر entity/concept کاملاً جدید و به‌اندازه کافی مهم است (قانون زیر)، صفحه جدید بساز و در `index.md` لینک بده.
4. یک خط در `log.md` اضافه کن: `## [YYYY-MM-DD] update | <خلاصه تغییر>`.

تغییرات trivial (typo، فرمت، rename بدون تغییر امضا) نیاز به آپدیت ندارند.
اگر چند فایل در یک مکالمه تغییر کردند، آپدیت‌های ویکی را یک‌بار در پایان مکالمه انجام بده.

## چه وقت صفحه جدید بساز
- فقط اگر ≥۳ جای دیگر قرار است به آن لینک بدهند، یا concept مستقلی با حجم قابل‌توجه است.
- در ۹۰٪ موارد به‌جای فایل جدید، صفحه موجود را آپدیت کن.
- هرگز صفحه‌ی trivial نساز (wrapper یک‌خطی، utility ساده) — در صفحه پدر یک bullet بنویس.

## ساختار صفحه‌ی entity
```markdown
# {نام}

> یک‌خطی توضیح هدف.

## مسئولیت‌ها
- ...

## وابستگی‌ها
- [[concepts/xxx]] — چرا
- [[entities/yyy]] — چطور

## قراردادها / Edge cases
- ...

## منابع کد
- `path/to/file.ts:42` — کلاس اصلی
```

## قواعد لینک (Obsidian-style)
- `[[entities/user]]` بدون پسوند `.md`.
- نام فایل: lowercase + hyphen (`auth-flow.md` نه `Auth Flow.md`).
- wikilinkهای نمونه داخل بک‌تیک/code block لینک واقعی محسوب نمی‌شوند.

## Lint دوره‌ای (وقتی کاربر گفت «ویکی رو بازبینی کن»)
1. orphan pages (بدون inbound link) — لینک بده یا حذف کن.
2. broken link — صفحه‌ی گمشده را بساز یا لینک را حذف کن.
3. تناقض بین صفحات — flag کن، نپرس، بهترین حدس را انتخاب کن و در log ثبت کن.
4. صفحات کهنه (کد مرتبط تغییر کرده ولی صفحه آپدیت نشده) — بازخوانی و sync.

## همگام‌سازی با GitHub Wiki
یک نسخهٔ آینه (mirror) از `overview.md`، `index.md`، `schema.md` و `log.md` در ویکی رسمی گیت‌هاب ریپو (`massoudsh/tarhyar` → تب Wiki) هم نگه‌داری می‌شود تا برای انسان‌ها هم بدون کلون‌کردن ریپو قابل مرور باشد. وقتی `docs/wiki/` به‌طور معنادار تغییر کرد (نه هر commit ریز)، این چهار صفحه را در ریپوی wiki (`massoudsh/tarhyar.wiki.git`) هم به‌روز و push کن؛ صفحات `entities/`/`concepts/` فقط وقتی تعداد و حجمشان قابل توجه شد به wiki اضافه می‌شوند.
